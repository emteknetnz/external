How a CMS 7 module replaces, extends and adds to admin UI components. The aims: a simple API, one way to do each thing, and YAML config that Silverstripe developers already know. A module writes React components and YAML. It has no entry file, no setup() function and no JS registration API.

The basis

Source: plan/index.md (section 5), plan/level5.md

  • Native ES modules and one import map that PHP writes before the first module script.
  • react, react-dom and @silverstripe/admin are shared through the import map. Modules do not bundle them.
  • A module can ship without a build step. Silverstripe publishes TypeScript types and a starter repo, not a build config or a CLI.
  • YAML replaces extra_requirements_javascript.
  • The module contract below must be right before CMS 7 ships. The loader can change at any time.

1. React only

Source: plan/level5.md ("The module contract")

Core accepts React components only. It does not accept objects with mount and unmount functions or custom elements, and it supplies no converters for other frameworks.

  • Three shapes would be three ways to do one thing.
  • Each extra shape needs its own bridge to forms, slots and extensions: more public API to document, test and support.
  • A module can still mount another framework inside a React component it owns. Core does not prevent it or support it.

2. Replace a component: a registry in YAML

One way to replace a core component or add a component for a module's own class: a registry in YAML, keyed by PHP class name. It works like the PHP Injector.

Source: plan/index.md (section 6), plan/level6.md

PHP today: replace a class

SilverStripe\Core\Injector\Injector:
  SilverStripe\Forms\TextField:
    class: App\Forms\FancyTextField

CMS 7: replace its component

SilverStripe\Admin\ComponentRegistry:
  SilverStripe\Forms\TextField:
    component: 'acme/fancy-fields:client/dist/FancyTextField.js'

Replace it only in some places with within

SilverStripe\Admin\ComponentRegistry:
  SilverStripe\Forms\TextField:
    component: 'acme/fancy-fields:client/dist/FancyTextField.js'
    within:
      DNADesign\Elemental\Models\BaseElement: 'acme/fancy-fields:client/dist/CompactTextField.js'
      App\Forms\AddressCompositeField: 'acme/fancy-fields:client/dist/AddressFinderField.js'
  • CompactTextField is used when the user edits any block. AddressFinderField is used for a TextField inside an AddressCompositeField, in any form.
  • Core walks up from the field, through its parent fields, to the record and then to the class that builds the form. The nearest match wins, and subclasses match.
  • Every key is a PHP class. There are no form names, scope strings or priority numbers.
  • A subclass with no entry uses its parent's entry. A project overrides a module with a later fragment, such as After: '#acme-fancy-fields'.

Wrap a core component: normal React

// FancyTextField.js
import { TextField } from '@silverstripe/admin';

export default (props) => (
  <div className="fancy">
    <TextField {...props} />
  </div>
);
Why not replace core files through the import map? Then every core JS file becomes public API, and a rename in core breaks a module with no clear error. Only components keyed by a PHP class can be replaced: a form field, an admin section, a record, an MFA method, a link type or a report.

3. JS extensions: like PHP extensions

A JS extension changes a value before core uses it, as updateCMSFields() does in PHP. YAML attaches it to a PHP class under extensions:. It is a file that exports an object with update* methods.

Source: plan/index.md (section 7), plan/level7.md ("JS extensions")

PHP extension

SilverStripe\CMS\Model\SiteTree:
  extensions:
    acme-page-extension: Acme\PageExtension
class PageExtension extends Extension
{
    protected function updateCMSFields(
        FieldList $fields
    ): void {
        $fields->removeByName('Content');
    }
}

JS extension

SilverStripe\Admin\ComponentRegistry:
  DNADesign\Elemental\Models\BaseElement:
    extensions:
      acme-block-extension: 'acme/module:client/dist/BlockExtension.js'
// BlockExtension.js
export default {
  updateTitle(title, type) {
    return `${title} (${type})`;
  },
};

A fuller example: change the action menu of a block

// BlockExtension.js
import MoveMenuItem from './MoveMenuItem'; // a React component in this module that opens its own modal

export default {
  updateActionMenu(items, block) {
    return [
      ...items.filter((item) => item.name !== 'duplicate'), // removes "Duplicate" from Elemental
      { name: 'copy-link', label: 'Copy link', onClick: () => navigator.clipboard.writeText(block.link) },
      { name: 'move', label: 'Move', Component: MoveMenuItem }, // the action menu decides what to do with each item
    ];
  },
};

Core calls updateActionMenu on each extension of BaseElement that has the method, as extend('updateActionMenu', ...) does in PHP.

The same rules as PHP

  • The first argument is the value to change. The others, such as block, are read-only. The method returns the changed value.
  • An extension on a class also applies to its subclasses.
  • Entries are keyed, so a project sets a key to null to remove an extension, or to another file to replace it.
  • Order is config order (Before and After).
  • Each list item has a name, so an extension can find an item to remove. The name of a core item is public API.
  • Methods are synchronous. Anything that waits for the user or the server is a component or a PHP action.
  • No app object: an extension imports plain functions, such as a toast or the API client, from @silverstripe/admin.
  • Data and lists that PHP controls stay in PHP. A JS extension is for behaviour that only exists in the browser.

4. Slots: add to a position

A slot is a named position in a core component where modules add their own components, such as a button in the block toolbar. Slots are declared under slots: on the PHP class that owns them.

Source: plan/level7.md ("Slots")

Add two buttons to the Elemental toolbar and remove one

# acme/module/_config/admin.yml
---
Name: acme-module
After: '#elemental'
---
SilverStripe\Admin\ComponentRegistry:
  DNADesign\Elemental\Forms\ElementalAreaField:
    slots:
      toolbar:
        acme-preview-button: 'acme/module:client/dist/PreviewButton.js'
        acme-share-button: 'acme/module:client/dist/ShareButton.js'
        elemental-add-block-button: null   # removes the "Add block" button from Elemental
// PreviewButton.js
export default (props) => <a href={props.page.previewLink}>Preview</a>;
  • A slot holds any number of components from any number of modules, shown in config order.
  • After: '#elemental' merges this fragment after Elemental's, so the null entry removes Elemental's button.
  • Slot names belong to their class, so they do not collide. Core passes props, such as the area and its page.

5. Checked against real code

Source: plan/level6.md, plan/level7.md ("How Elemental maps to this")

Every JS extension point in recipe-cms and Elemental is covered by components, extensions and slots, with a few rules: PHP resolves the registry and sends file URLs to the browser, one PHP class has one view, and within walks from the field up to the class that builds the form. For Elemental:

  • The 15 internal components it registers only to inject them become plain imports.
  • The block actions become items of updateActionMenu on BaseElement.
  • The Redux reducer, the Entwine mount and the save coordination with the page form go with the REST API.

Minor points

Source: plan/level5.md ("Load sequence", "Browser support")

  • Cache key: a hash of the file content, not the Composer package versions. The version does not change for dev-main or project code.
  • es-module-shims: current browsers do not need it. It is added only if the supported browser list needs it.
